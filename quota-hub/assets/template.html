要脚本化又要省心，这是答案。一次配置，脚本只认一个 base_url + 一个 key，新增平台改配置不动代码。

各平台接入方式速查

按兑现方式分类。标「网页」的意味着脚本拿不到，编排流水线里只能人工跑。

按当前方案导出网关配置

生成 LiteLLM 的 config.yaml 和只认一个端点的 runner。配置里已按方案的平台顺序写好 fallback 链。

为什么用 openai/ + api_base 而不是各家专有 provider 名：绝大多数国内外平台都是 OpenAI 兼容端点， 这是 LiteLLM 里唯一不会因为 provider 命名变化而失效的写法。
安全提醒：用官方 Docker 镜像并固定版本，不要用 latest 跑生产。2026-03 曾有投毒版本在 PyPI 存活约 40 分钟。

为什么需要这一页

额度表再准，接不通也是零。本轮核实里，MiniMax、讯飞、Kimi、LongCat 四家的 base_url 都出现了 2~3 个互相冲突的版本， 而 DeepSeek、Groq、Kimi 的 model id 又刚经历过一轮集体退役。这一页只做两件事：给出以官方文档为准的接入硬事实， 以及导出一个能用你自己的 key 跑一遍的自检脚本。

接入总表

每一条都挂着官方出处与核实日期。标了「口径冲突」的说明多个来源说法不一致——这类不要照抄，去控制台确认。

把对错交给脚本

下载三件套：verify_all.py 逐个探测已配置的端点，.env 模板 照着填 key， 自检脚本默认用 GET /models ——不消耗任何 token 与请求次数，失败时自动降级为最小请求重试。

三种错误的修法完全不同，先分清是哪一类：
401 = key 无效或被吊销 → 去控制台重新生成
403 = key 有效但没开通这个模型 / 地域不对 → 去控制台开通
404 = base_url 写错了 → 改端点，跟 key 无关（百炼的免费额度仅限华北 2，用错地域不报错但直接计费）
429 = 配置是对的，只是限速或额度耗尽 → 降并发或等重置

这些是本轮核实中多个来源互相打架的地方。处理方式统一为：以官方页面为准，并在上生产前用自检脚本确认一次。

已开通清单

开关控制是否计入产能估算
说明：清单记录「哪些平台已开通」，用量靠自己登记（支持 1.5万 / 200k / 3000 这些写法）， 不采集任何 Key、也不调用官方接口。每日刷新型的「今日已用」跨天自动归零，一次性礼包的「已用」累计不清零。 所有数据保存在浏览器本地（localStorage），换设备不会同步。 重置时间是按各平台公开的重置节奏推算的估算值，不接入官方接口——所以它是个决策辅助，不是监控系统。
